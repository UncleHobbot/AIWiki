## Summary
A free 12-lecture practical course by Walking Labs that synthesizes OpenAI and Anthropic harness engineering research into an actionable curriculum for making AI coding agents reliable through environment design, state management, verification, and session discipline.

## Key Ideas
- **The five-subsystem harness model**: Instructions (AGENTS.md), Tools, Environment, State (PROGRESS.md), Feedback (verification commands). Removing any one subsystem degrades agent performance — experiments show success rates drop from ~80–100% to 20% without the full set.
- **The repo is the single source of truth**: anything not in the repository does not exist for the agent. Use a "cold-start test" — open a fresh session and check if it can answer five basic questions (what is this project? how do I run it? how do I verify it?) using only repo contents.
- **Split instructions across files, not one giant AGENTS.md**: a 600-line instruction file hurts performance due to lost-in-the-middle effects (Liu et al. 2023), context budget starvation, and rule priority conflicts. Keep AGENTS.md to 50–100 lines; put module-specific constraints in per-directory `ARCHITECTURE.md` files.
- **WIP=1 is the default safe setting**: agents that activate multiple tasks simultaneously see a 37% lower completion rate. Anthropic data: lines of code generated by agents is weakly negatively correlated with features actually completed. Enforce one active task at a time, with explicit completion evidence (executable verification commands, not "the code looks fine").
- **Premature victory declarations are systematic**: neural networks are overconfident by design (Guo et al., 2017 ICML). Use a three-layer termination check — static analysis, runtime behavior, end-to-end flow — before accepting "done." Separate the worker from the checker (independent evaluator agent is more effective than self-evaluation).
- **Clean state at every session end**: without active cleanup, build pass rates degrade from 100% to 68% in 12 weeks; with a clean-state discipline, they stay at 97%. Five dimensions: build passes, tests pass, progress recorded, no stale artifacts, standard startup path available.

## Details

### The Core Harness Loop

The course frames the harness as a closed-loop system, not just a prompt file. The loop is: Task Description → Context Assembly → Tool Execution → Feedback → Progress Update → next iteration. Crucially, the model sees only what the harness puts in front of it. The harness determines context quality, tool availability, verification strictness, and state continuity across sessions.

The five subsystems map directly onto common agent failures: agents that misunderstand tasks lack an Instructions subsystem; agents that can't run verification lack a Feedback subsystem; agents that re-explore the same project structure every session lack a State subsystem.

### Repository as Spec (Lecture 3)

The "knowledge visibility gap" — the fraction of project knowledge not in the repo — is the primary driver of agent failure on real codebases. Architectural decisions scattered across Confluence, Slack, and engineers' heads are invisible to the agent. The practical fix is not "write more docs" but "put decisions in the right place": short ARCHITECTURE.md files co-located with the code they describe, a centralized CONSTRAINTS.md with hard rules in MUST/MUST NOT language, and a PROGRESS.md tracking current session state.

State management should follow ACID principles from database theory: Atomicity (one logical operation per commit), Consistency (verify invariants after each operation), Isolation (per-agent progress files to avoid concurrent write conflicts), Durability (cross-session knowledge in git-tracked files, not in session memory).

### Instruction File Architecture (Lecture 4)

The vicious cycle: agent makes a mistake → add a rule to AGENTS.md → repeat until the file is 600 lines and performance degrades. The "Lost in the Middle" research shows LLMs underutilize information in the middle of long prompts. The solution is contextual scoping: AGENTS.md is the landing page (50–100 lines), not the encyclopedia. Deep constraints live in per-directory files the agent reads on demand.

### Task Boundaries and WIP=1 (Lecture 7)

Agents have a natural impulse toward "while I'm here" scope expansion. Claude Code asked to "add user registration" reliably expands into six simultaneous half-done tasks. The mathematical basis is Little's Law: if work-in-progress L is too high, lead time W per task increases proportionally. The harness fix: write explicit WIP rules in CLAUDE.md, require executable completion evidence for every feature, and externalize the scope surface as a machine-readable file so any new session can see which task is active and what "done" means.

### Verification Discipline (Lectures 9–10)

The three-layer check mirrors test pyramid thinking but applied to agent termination: Layer 1 is static analysis (cheap, necessary, insufficient); Layer 2 is runtime behavior (test execution, app startup, critical path); Layer 3 is system-level end-to-end (the only layer that catches interface mismatches, state propagation errors, and environment dependencies). "Refactoring while we're at it" is specifically harmful because it blurs the boundary between verified and unverified code.

Error messages for agents should include fix instructions, not just failure signals: instead of "Test failed," use "Test failed: POST /api/reset-password returned 500. Check email service config in environment variables."

### Session Discipline (Lecture 12)

Every session exit requires passing a five-dimension clean-state checklist (build, tests, progress, artifacts, startup). A project developed without this discipline shows exponential entropy growth: 60+ minute new-session startup times and 68% build pass rates by week 12. With the discipline: 9-minute startup and 97% build rates. The course also recommends monthly harness simplification reviews — as model capabilities improve, some harness components that were essential six months ago become unnecessary overhead.

## Краткое описание
Бесплатный 12-лекционный практический курс от Walking Labs, синтезирующий исследования OpenAI и Anthropic по harness engineering в конкретную программу обучения: как сделать AI-агентов надёжными через проектирование среды, управление состоянием, верификацию и дисциплину сессий.

## Ключевые идеи
- **Пятисистемная модель жгута**: Инструкции (AGENTS.md), Инструменты, Среда, Состояние (PROGRESS.md), Обратная связь (команды верификации). Убери любую одну — производительность агента падает. Эксперименты показывают: без полного набора успешность задач снижается с ~80–100% до 20%.
- **Репозиторий — единственный источник истины**: всего, чего нет в репозитории, для агента не существует. «Тест холодного старта» — открыть новую сессию и проверить, может ли агент ответить на пять базовых вопросов, используя только содержимое репозитория.
- **Разделяй инструкции по файлам, а не в один гигантский AGENTS.md**: файл на 600 строк снижает качество работы из-за эффекта «потерянного в середине» (Liu et al., 2023), нехватки бюджета контекста и конфликтов приоритетов правил. AGENTS.md — 50–100 строк; специфические ограничения каждого модуля — в ARCHITECTURE.md рядом с кодом.
- **WIP=1 — безопасная настройка по умолчанию**: агенты, запускающие несколько задач одновременно, показывают на 37% более низкую завершаемость. Данные Anthropic: количество сгенерированных строк кода слабо отрицательно коррелирует с числом реально выполненных фич. Одна активная задача за раз с явными критериями завершения (исполняемые команды верификации, не «код выглядит нормально»).
- **Преждевременные объявления победы носят системный характер**: нейросети систематически переоценивают уверенность (Guo et al., ICML 2017). Трёхуровневая проверка завершения: статический анализ, проверка поведения в рантайме, сквозное тестирование. Разделяй «исполнителя» и «проверяющего».
- **Чистое состояние в конце каждой сессии**: без активной дисциплины очистки за 12 недель успешность сборки падает с 100% до 68%; с дисциплиной — остаётся на уровне 97%. Пять измерений: сборка, тесты, прогресс, артефакты, стартовый путь.

## Подробнее

### Петля жгута

Курс описывает жгут как систему с замкнутым контуром управления: Описание задачи → Сборка контекста → Выполнение инструментов → Обратная связь → Обновление прогресса → следующая итерация. Пять подсистем соответствуют типичным видам отказа агентов: неправильно понятые задачи — отсутствие подсистемы инструкций; неспособность запустить верификацию — отсутствие подсистемы обратной связи; повторное исследование структуры проекта в каждой сессии — отсутствие подсистемы состояния.

### Репозиторий как спецификация (Лекция 3)

«Разрыв видимости знаний» — доля знаний о проекте, отсутствующих в репозитории, — главный драйвер отказов на реальных кодовых базах. Архитектурные решения, рассредоточенные по Confluence, Slack и головам инженеров, невидимы агенту. Практическое решение: короткие ARCHITECTURE.md рядом с описываемым кодом, централизованный CONSTRAINTS.md с жёсткими правилами в формате MUST/MUST NOT, PROGRESS.md для отслеживания текущего состояния сессии. Управление состоянием рекомендуется строить по ACID-принципам из теории баз данных.

### Архитектура файлов инструкций (Лекция 4)

Порочный цикл: агент делает ошибку → добавляем правило в AGENTS.md → повторяем, пока файл не вырастет до 600 строк и производительность не ухудшится. Исследование «Lost in the Middle» показывает, что LLM хуже используют информацию из середины длинных промптов. Решение: AGENTS.md — страница навигации (50–100 строк), глубокие ограничения — в файлах директорий, которые агент читает по требованию.

### Границы задач и WIP=1 (Лекция 7)

У агентов есть естественный импульс к расширению задач «раз уж я здесь». Математическое обоснование — закон Литтла: при высоком WIP время на выполнение каждой задачи растёт пропорционально. Решение в жгуте: явные правила WIP в CLAUDE.md, исполняемые критерии завершения для каждой фичи, выражение поверхности задач в машиночитаемом файле.

### Дисциплина верификации (Лекции 9–10)

Трёхуровневая проверка завершения: Слой 1 — статический анализ (дёшево, необходимо, недостаточно); Слой 2 — проверка поведения в рантайме (запуск тестов, старт приложения, критические пути); Слой 3 — сквозное тестирование (единственный уровень, который выявляет несовместимость интерфейсов, ошибки распространения состояния, зависимости от среды). Сообщения об ошибках для агентов должны содержать инструкции по исправлению: не «Тест не прошёл», а «Тест не прошёл: POST /api/reset-password вернул 500. Проверьте конфигурацию email-сервиса в переменных среды».

### Дисциплина сессий (Лекция 12)

Каждая сессия должна завершаться проверкой пяти измерений чистого состояния (сборка, тесты, прогресс, артефакты, стартовый путь). Ежемесячно рекомендуется аудит упрощения жгута: по мере роста возможностей моделей ограничения, ранее необходимые, становятся избыточными.

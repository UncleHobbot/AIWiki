What is RAG?

Retrieval-Augmented Generation

Introduced by Lewis et al. (Facebook AI Research, 2020). A technique that grounds LLM responses in a specific document corpus — without fine-tuning the model on that corpus.

  • Split documents into chunks → convert each chunk into a numeric embedding → store in a vector database
  • At query time: embed the user's question, find the most similar chunks via cosine similarity, inject them into the LLM prompt as context
  • The LLM answers using retrieved chunks as evidence — it doesn't rely on memorized training knowledge
  • Works for any domain without retraining — swap the corpus, keep the model
The core promise: keep an LLM factual and current by retrieving evidence at query time, rather than baking domain knowledge into model weights. — Lewis et al., "Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks", NeurIPS 2020

RAG shines when: corpus is large (millions of docs), changes frequently, or precise citations back to source chunks are required.

RAG's blind spot: every query re-derives understanding from scratch — cross-source synthesis, longitudinal reasoning, and accumulated insight are not preserved between calls.

The Problem

Knowledge that disappears

  • Every LLM session starts cold — no memory of previous reasoning
  • RAG re-derives conclusions from raw text on every query
  • Humans build wikis, then abandon them when maintenance costs grow
  • Cross-references rot; contradictions accumulate silently
"No existing AI-scientist tool persists knowledge retrievably across runs — they begin from scratch each session." — PARNESS authors, arXiv:2605.05258

The RAG Bottleneck

  • Retrieval returns chunks, not synthesized understanding
  • 85% of agent effort wasted on retrieval overhead (Pinecone, 2026)
  • 50–60% task completion rate with agentic RAG at scale
  • Vector indexes require specialized infrastructure
  • Cross-source synthesis is re-done from scratch every call

The Core Idea

The Compilation Analogy

You don't re-run source code on every execution — you compile it once into a binary and run that.

// Software engineering compile(source_code) → binary run(binary) // fast, reusable // LLM Wiki ingest(raw_docs) → wiki_pages query(wiki) // no re-derivation

Published April 2, 2026

GitHub Gist titled llm-wiki.md — an "idea file" designed to be pasted into any LLM agent, which then instantiates the pattern for its specific domain.

Three-Layer Architecture

1
Raw Sources → inbox/ + sources/
Immutable ground truth. Web clips, PDFs, transcripts, tweets. Never edited — only appended to. The "source code."
▼
2
Wiki → wiki/
LLM-owned markdown files. Cross-referenced, bilingual, synthesized. The "compiled binary." Knowledge accumulates — not re-derived per query.
▼
3
Schema File → CLAUDE.md / AGENTS.md
Controls context injection. Tells the agent: how to structure pages, how to link concepts, what to do with each source type. The critical innovation — one line per domain.

Navigation files: index.md — content catalog of all pages  ·  log.md — append-only chronological history. Together they let the LLM navigate ~100–500 sources without embedding infrastructure.

Three Operations

INGEST
New source → LLM reads it → writes or updates 10–15 wiki pages.

Cross-references are pre-built. Contradictions flagged immediately. Each ingest makes the whole richer.
→
QUERY
LLM reads compiled wiki, synthesizes answer.

Good answers get filed back as new wiki pages — the system self-documents its own reasoning.
→
LINT
Periodic audit: find contradictions, orphan pages, stale claims, broken cross-links.

Non-optional. Without Lint, hallucinations bake in permanently.

Key risk: In pure RAG a hallucination affects one answer. In LLM Wiki, a misunderstood source can get written as "fact" and propagate via cross-links to 15 other pages before anyone notices. Lint is your safety net.

Setup in 5 Steps

1
Install Obsidian (free) — create a new vault. Create three folders: raw/, wiki/, templates/.
2
Paste Karpathy's gist into Claude Code. Ask it to create claude.md tailored to your domain — answer its clarifying questions.
3
Drop your first source into raw/ — markdown clip, PDF, or text. Run: "I just added a new source. Please update the wiki."
4
Claude writes 5–15 wiki pages, updates index.md, logs the run. Open Obsidian graph view to see the knowledge structure forming.
5
Repeat: add sources, run "Please lint the wiki." periodically, ask synthesis questions. The wiki compounds.

Tools

Viewer: Obsidian — graph view, backlinks, search. Not an AI tool — just a markdown reader.

Agent: Claude Code, Codex, or Cursor. Anything that reads and writes files on your machine.

Scale limit: ~100–200 sources without embedding infra. Beyond that: add qmd for hybrid BM25/vector search.

Self-Improvement Loop

Adopt Useful Skills

The wiki observes which explanations resonate — frequently queried pages get richer cross-references. The agent develops domain intuition from patterns in query history. Knowledge gaps in the wiki surface as missing pages in broken-link audits.

"Steal" Ideas from Similar Projects

PARNESS introduced contradiction-indexed cross-run memory. SurveyGen-I introduced "do not re-explain" term memory. LightRAG introduced dual-level entity/concept graphs. Each is an importable pattern — no vector DB required.

Learn from History of Sessions

log.md is a complete audit trail. Entries created vs. updated ratio reveals whether the wiki is growing healthily. Orphan counts track integration quality. Broken links track debt accumulation.

Adjust Behavior from Failures

Hallucinations that survived into wiki pages become training examples for the Lint prompt. The CLAUDE.md schema evolves based on observed failure modes — tightening source-tier rules, adding category decision trees, refining the bilingual template.

The compounding effect: Each new source makes the wiki richer. Each query that gets filed as a new page adds cross-references. Each lint pass removes noise. The system gets better at being a wiki over time — not just bigger.

Open Gaps to Close

Contradiction Detection

Currently: caught manually during Lint. Academic solution: KARMA's 9-agent consensus — extract core claims from each new entry, compare against same-category entries.

scripts/check_conflicts.py → auto-populate ## Debate in both entries

Relational Retrieval

Current search: full-text ripgrep. Misses: "which tools use RAG?" LightRAG approach: after each entry, run relation-extraction Claude call → write to .state/relations/slug.json.

No vector DB or graph DB required.

Digest Coherence

Problem: weekly digest re-explains concepts defined last week. SurveyGen-I fix: after each digest, write digests/memory.json of all defined terms → inject as "do not re-explain" constraint next run.
